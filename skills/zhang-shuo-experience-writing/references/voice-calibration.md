# 写作校准记录

状态：v1.5。来自 KIN 项目申请描述、BRM 简历版、SPPS 工程项目长版及简历版、QQ 灵犀项目描述及简历版的用户修改和最终确认。这里记录用户修改揭示的稳定偏好，不把任一项目的具体事实自动迁移到其他经历。已确认参考见 [approved-kin-long-form.md](approved-kin-long-form.md)、[approved-kin-resume-brm.md](approved-kin-resume-brm.md)、[approved-spps-long-form.md](approved-spps-long-form.md)、[approved-spps-resume-brm.md](approved-spps-resume-brm.md)、[approved-qq-lingxi-long-form.md](approved-qq-lingxi-long-form.md) 与 [approved-qq-lingxi-resume-brm.md](approved-qq-lingxi-resume-brm.md)。

## 用户修改揭示的差异

| 原稿倾向 | 用户修改方向 | 可复用规则 |
|---|---|---|
| 把未接电话写成“联系失败、不了解情况” | 补出“面对未知的恐惧感” | 不停在信息缺口，继续追问它让具体的人感受到什么。 |
| 直接说“增加幸福感” | 改成“增加家人之间的连接，从而创造幸福” | 使命必须有中间机制，避免抽象价值悬空。 |
| 把用户打开概括为“处理告警或随手查看” | 强调“不是被迫处理告警，而是因为关心、好奇和参与感主动打开” | 写清主动行为的内在动机，这是产品长期价值的一部分。 |
| 一句话同时容纳动机、动作和结果 | 主动拆开“随手看看”与“产生话题、增加交流” | 关键因果可分句强调，但润色时补齐主语和连接关系。 |
| 同时比较米家与快手 | 只保留米家 | 优先使用最接近产品形态或战略问题的单一 benchmark，避免数字喧宾夺主。 |
| 使用“产品同时……” | 删除不必要的“同时” | 减少机械过渡词，能直接说就直接说。 |

## 第二轮：简历压缩与可面试性

| 原稿倾向 | 用户修改方向 | 可复用规则 |
|---|---|---|
| 为贴近 BRM，把具体生活语言改写成岗位框架词 | 保留“没听见还是出了危险”等人的原话 | 岗位匹配通过选择什么事实来写体现，不通过把原话翻译成抽象术语体现。 |
| 为压缩而删除市场判断 | 恢复目标人群、规模情景、相邻消费、benchmark 与 Agent 时代注意力判断 | 压缩优先删次要模块，不删本人最独特、最能展开的判断。 |
| 用 OEM/API 等实施路线补齐商业链条 | 删除本人不掌握、被追问时讲不透的实施内容 | 简历只放本人可以连续接受追问的内容；项目完整性不能替代候选人的真实 ownership。 |
| 默认三条 bullet 应接近等长 | 允许核心项目更长，其他经历更短 | 版面服从证据密度；只要长段仍是一条因果链，就不为形式等长牺牲关键判断。 |
| 罗列 AI 执行事项但不写最终交付 | 补出可交互原型、品牌片、商业方案和上线案例页 | 先分清本人判断与 AI 执行，再用可检查的交付物结束。 |

本轮进一步确认：简历不是项目目录，也不是完整商业计划书。它的作用是留下少数面试入口，使招聘者愿意追问，而用户能用真实事实继续讲透。

## 第三轮：工程项目的正序叙事与设计权

| 原稿倾向 | 用户修改方向 | 可复用规则 |
|---|---|---|
| 为了突出结果而倒叙，读者还不知仪器如何工作就先看到结果 | 恢复“接到任务—学习原理—设计整机—拆解任务—集成交付”的正序 | 陌生工程项目先建立理解再讲结果，不机械奉行结果前置。 |
| 用“协调机械、加工、电控协作者”概括人员关系 | 补出本人完成总体设计和选型，将动作、产品形态、参数、接口与交付标准下发给协作者 | “协调”不能代替决策权。当本人是设计与结果负责人时，要写清谁定义、谁实现、谁验收。 |
| “机械设计加工由协作者完成”把总体设计权一并让出 | 区分总体方案/技术指标/接口与 CAD 细化/定制加工/底层驱动 | 如实承认专业实现不等于削弱系统 owner；设计权和亲手执行要分开表达。 |
| 只写“大幅降低成本”或笼统写“10 倍替代” | 用同类具体部件的实际采购价、公开价与计算降幅 | 量化必须有边界：可写“近同规格 FEP 管单项降低约 88%”，不外推为整机或全部部件降幅。 |

本轮还确认：有效数字要对应一种可理解的能力——团队人数对应任务管理，供应商数量对应采购复杂度，资源规模对应责任边界，单项降本对应选型判断，集成周期和操作时间对应交付效率。不为数字密度罗列文档数、发票数等无法改变招聘判断的计数。

## 第四轮：工程长稿压缩为 BRM 简历

| 原稿倾向 | 用户修改方向 | 可复用规则 |
|---|---|---|
| 把长稿中的技术清单和全部过程平均压入简历 | 只保留总体设计与领导、资源与流程、交付与效率三类证据 | 简历不是工程说明书；保留能形成不同面试入口的事实，把泵阀数量、脚本数量等细节留给追问。 |
| 为了量化只写一个 FEP 管降本案例 | 先写泵、管路、阀门和多类耗材的国产替代，再用 FEP 管证明其中一个判断 | 当实际工作范围大于可量化样例时，先写范围、后写例子；不能让证据样本反过来缩小 ownership。 |
| 从一个样例的 88% 推断整套国产替代的总体降幅 | 明确“其中以……为例，单项采购成本降低约 88%” | 数字只承担它能证明的结论，既不用模糊词浪费证据，也不跨边界外推。 |

本轮进一步确认：一项工程经历可以用三条构成互补证据，而不是三次重复“负责项目”。第一条回答“你定义了什么、怎样让专业人员配合”；第二条回答“你管了多少资源、改变了什么流程、怎样做成本判断”；第三条回答“最后多快交付、效率改变多少”。

## 第五轮：从具体产品到 big picture

| 原稿倾向 | 用户修改方向 | 可复用规则 |
|---|---|---|
| 只写产品功能和原型交付 | 补回外部 AI 的用户理解、QQ 的真实关系资产与智能连接层判断 | 用户习惯从具体问题上推到平台资产和生态位置；当推演有明确机制支撑时，应保留一条战略判断。 |
| 用“有战略思维、看到 big picture”直接评价本人 | 用“具体问题 → 产品机制 → 独特资产 → 平台机会”展示 | 不写自我形容词，让推理链本身证明战略能力。 |
| 把匹配、Agent 协商、风险与输出全部塞进一个长句 | 先写匹配完成，再明确谁与谁协商、产生什么结果 | 复杂产品链路要拆句并写出动作主体，不能靠连续逗号让读者自行还原。 |
| 按 Git 首尾日期写连续开发周期 | 按本人实际投入写“累计约10天”，并注明分阶段集中完成 | 日历跨度不等于有效工作时长；有明显空档时使用累计投入或只写月份。 |
| 对外同时写 ChatGPT/Codex | 统一写 ChatGPT | 用户希望公开求职文本使用公众更熟悉的产品名；除非技术审计需要，不展开内部工具名称。 |

本轮进一步确认：big picture 是用户稳定的思考特点，但成稿不能从愿景开场。先让读者理解一个真实问题和产品怎样解决，再说明哪些独特资产使它可能成长为更大的平台，最后用原型或结果把判断落回现实。

## 第六轮：AI 产品项目的简历压缩

| 原稿倾向 | 用户确认方向 | 可复用规则 |
|---|---|---|
| 把长版的产品、战略、协作与交付平均压入多条 bullet | 用两条分别承载产品机制，以及平台判断、ownership 与结果 | 两条不等于删掉一半逻辑；每条只承担一种主要阅读任务，合起来形成完整判断。 |
| 压缩时优先保留功能，战略被当作可删愿景 | 保留外部 AI 的用户理解与 QQ 真实关系资产之间的连接 | 有产品机制和独特资产支撑的 big picture 是候选人的关键贡献，应进入简历而不只留在长稿。 |
| 以项目跨越的日历天数表现速度 | 使用“累计约10天完成两轮集中迭代” | 当投入分阶段且中间停工，累计有效工作时间比首尾日期更能说明执行速度。 |
| 把所有机制与交付细节塞进简历证明完整性 | 留下核心链路与可交互原型、复赛结果，把其余内容留给追问 | 简历为面试建立入口；长版与事实源负责支撑展开，不必在首层复述全部材料。 |

本轮进一步确认：对 AI 产品经历，简历可以先用一条让陌生人真正理解“系统怎样替用户完成连接”，再用一条回答“为什么这可能成为更大的平台、候选人拥有什么决策权、最后交付了什么”。具体机制与 big picture 都不能被通用产品术语替代。

## 润色时怎样保留原意

用户的修改优先级高于原稿。只修复下面三类问题：

1. **残句**：例如“完全不知道……”可并入前句，用冒号或破折号承接。
2. **搭配不顺**：例如“是一种面对未知的恐惧感”可改为“更是面对未知时的恐惧”。
3. **因果连接不清**：例如“是主动的因为……”可改为“而是出于……主动……”。

不要借润色做下面这些事：

- 删除“恐惧、负担、幸福”等有立场的词；
- 把“主动打开”弱化成“提升使用频率”；
- 用“用户痛点、价值赋能、生态闭环”等泛化术语替换具体行为；
- 恢复用户已经删掉的比较、解释或防御性话语。

## 本轮推荐句式

这些句式展示语法修复方向，不要求机械复用：

- “子女面对的不只是一次联系失败，更是面对未知时的恐惧——完全不知道父母此刻在哪里、正在做什么：只是没有听见、没有带手机，还是确实遇到了危险？”
- “KIN 的使命不只是降低风险，更是通过技术增加家人之间的连接，从而直接创造幸福。”
- “KIN 希望用户打开产品，不是为了被动处理告警，而是出于关心、好奇和参与感，主动看看父母今天过得怎样。”
- “生活片段由此自然变成话题，增加子女与父母之间的交流。”

后续每完成一项经历的用户改稿，只追加能够改变未来写作决策的新偏好；不把一次性的词语选择累积成僵硬模板。
